# v0.4: requirements to control/sequence candidates

The connected host agent interprets customer language and calls the following
tools. Users do not need to provide a complete I/O table or hand-author JSON.
Missing recipe fields resolve to documented draft defaults returned as
`design.resolved_spec`, `defaults_used` (control recipes), and `assumptions`.
The high-level MCP tools also save a companion `.ldr.design.json` next to each
file, so resolved assumptions and resource assignments survive the chat.
These defaults are not engineering approval or a claim of safety certification.

## New generation tools

- `generate_control_ldr`: start_stop, set_reset, toggle, rising_edge, falling_edge,
  on_delay, off_delay, pulse, counter, forward_reverse and star_delta.
- `generate_sequence_ldr`: 1..16 ordered steps with individual outputs, tick
  durations, Boolean completion feedback, active-time timeout, pause/resume,
  latched abort, reset and completion. Step state is snapshotted to prevent
  multiple transitions cascading in one scan.
- `generate_ldr` remains available for custom/composed IR.
- `generate_system_ldr`: combines up to 24 independent recipes, reserving all
  explicitly chosen Y/M/T/C ranges first and allocating missing addresses without
  collisions. Explicit overlaps are errors; inputs may intentionally be shared.

Recipe SET/RST and edge functions compile into Boolean networks; they do not
claim new native opcode coverage. Pulse outputs are non-retriggerable while
active and have a reset scan after completion. Forward wins simultaneous
direction starts. Star/delta outputs are main, star and delta in consecutive
Y addresses; external mechanical/electrical interlocks remain necessary.

## Pause/resume: explicit time-base dependency

The sequence retains **whole clock-pulse counts** during pause, turns outputs
off, and ignores pulses while paused. Resuming with clock already high cannot
generate a spurious tick. It does NOT implement a native retentive timer, save
fractions of a tick, or retain state across power loss.

Default X4 must be supplied with an observable external clock, one rising edge
per 100ms. Both high and low must be sampled. The MCP does not configure or
physically supply this signal. If a customer's hardware has no such clock,
this candidate is not an equivalent turnkey solution: the dependency must be
reported, not hidden. No new firmware opcode is guessed to bypass this limit.

Default X0=start, X1=pause, X2=reset, X3=abort; active-high. Completion expressions
can refer to other X inputs (e.g. X5 for liquid level). Omitted step timeouts use
max(100, 3*step ticks), capped at 32767. Timeout pauses along with the process;
completion wins if it occurs at the timeout tick. Fault M6 remains latched until
reset. These are design assumptions, not universally safe process settings.

## Reproduce the examples

```powershell
uv sync --locked
uv run winproladder-setup check
uv run python scripts/generate_control_examples.py --root C:\VM_Share --prefix v04
```

This uses actual MCP calls to produce 13 .ldr files with companion design JSON
reports under the root's artifacts directory. New names are required for a rerun;
existing files are never overwritten. The JSON contains allocated resources,
defaults, file hashes, warnings and any requested acceptance result.

## Scope

This broadens common control functions, not the entire FATEK instruction set.
General arithmetic, MOV, indirect addressing, native retentive timers,
communications, positioning and many hardware-specific functions remain
unsupported. Existing .ldr byte round trips and scan-model tests are not proof
of WinProLadder GUI import, real timing accuracy or machine safety. GUI import
verification remains outstanding and is explicitly false in recipe reports.
